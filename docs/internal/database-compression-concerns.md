# Database compression: concerns and evidence

This matrix explains which existing contracts a smaller AgentsView archive must
preserve and which reports motivate the
[database compression proposal](database-compression-proposal.md). It separates
existing upstream work from proposed changes and from checks that have not
been completed. It is a maintainer design reference, not a claim that the
proposal is implemented or ready to migrate an archive.

The selected direction is metadata normalization first: internal integer
references retain permanent mappings to exact opaque external IDs, and compact
canonical digest representations retain an exact fallback for other values.
No history, identity records or tombstones are pruned. A typed payload codec is
optional and requires separate validation. Page or VFS compression remains a
separate feasibility study. This document claims no new measured savings.

## How to read the requirements

The [proposal's requirements](database-compression-proposal.md#what-must-remain-true)
own the design and acceptance criteria. These labels connect them to the evidence
below.

| Requirement | Contract |
| --- | --- |
| R1 | Exact logical bytes; all external IDs, history, tombstones and curation. |
| R2 | Metadata queries without payload decoding; complete search and export semantics. |
| R3 | Bounded memory, CPU and WAL work; cancellation and concurrent access. |
| R4 | Crash-safe archive-only migration and reversal; ownership and peak-space safety. |
| R5 | Every ingestion, copy, ATTACH and maintenance path; stable mirror fingerprints. |
| R6 | Release, tool and format compatibility, including old-writer fences. |
| R7 | Honest total-footprint and performance measurements. |

A **hard requirement** below comes from preserving the requested lossless,
queryable archive or an explicit existing contract. A reporter's proposed
implementation, a tentative maintainer preference and a draft roadmap are
identified as such; they are not interchangeable with accepted behavior.
Historical automated review findings describe the commits reviewed at that
time. They are evidence of failure modes, not instructions or assertions that
the final merged code still has those bugs.

the relevant PRs need individual verification before any hosted deployment
claim. [#2719](https://github.com/kenn-io/agentsview/issues/2719) was closed on
November 8, but this research did not establish its final fixing PR. Its report
is retained as a regression precedent, not an assertion of a current defect.

## What this evidence does not establish

No new archive layout, codec, migration, reversal or compatibility layer is
implemented by this proposal. The research does not establish a new compression
ratio, total-footprint saving, migration duration, peak-space requirement or
performance improvement.

The metadata normalization phase still needs exact identity and digest
round-trip proofs, query-plan and index-size measurements, complete history and
curation comparisons, and migration/reversal fault tests. The optional codec
additionally needs bounded decoding, full search/export parity and reader/writer
format compatibility. Existing processes and external SQLite tooling require
an explicit compatibility story; a format gate alone only rejects new opens.

Deleting transcripts, stripping images, narrowing retention, disabling search or
embeddings, pruning authoritative tombstones, and moving the only queryable copy
to a remote service do not satisfy this proposal. Derived-cache retirement and
existing asset offload may be useful independently, but their savings and
availability effects must be reported separately.

Use the [proposal](database-compression-proposal.md) for the chosen design,
phase gates and decision criteria, and the
[storage rules](../agents/storage.md) and
[background-work rules](../agents/background-work.md) for existing implementation
contracts.
